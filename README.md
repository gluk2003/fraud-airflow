# HW3 — антифрод с переобучением в Apache Airflow

Поток `transactions → скоринг → scores` в Kafka; три DAG управляют поставкой размеченных месяцев, обучением и Data Quality. Модель — Random Forest на CPU. В Kafka и таблице результатов есть `score`, `fraud_flag`, `model_version`. Смена версии происходит без перезапуска скорера.

## Запуск

Нужны Git, Docker Engine/Desktop и Docker Compose v2. Рекомендуется выделить Docker 4 CPU, 8 GB RAM и 10 GB диска. Порты 8081 и 8082 должны быть свободны. Для первого запуска нужен интернет для образов и Python-пакетов. CSV уже в репозитории, Kaggle и внешние ключи не нужны.

```bash
git clone https://github.com/gluk2003/fraud-airflow.git
cd fraud-airflow
docker compose up -d --build
docker compose ps -a
```

Дождитесь `healthy` у Kafka, PostgreSQL, Airflow webserver и scheduler. Контейнеры с суффиксом `init` завершаются с кодом 0 — это штатно. Первый запуск дольше из-за загрузки образов и установки зависимостей. Ошибки видны через `docker compose logs --tail=100`.

| Сервис / результат | Адрес |
|---|---|
| Airflow UI | http://localhost:8081 — `admin` / `admin` |
| HTML DQ и JSON сравнения моделей | http://localhost:8082 |
| Опубликованные модели | `./artifacts/models/` |
| Указатель модели и окна | `./artifacts/models/latest.json` |
| Витрина и скоры | `./artifacts/warehouse.db` |
| Снимки окон и кандидаты | `./artifacts/runs/<hash run_id>/` |

Все сервисы подключены к общей сети Compose. PostgreSQL хранит метаданные Airflow. Размеченная витрина и результаты скоринга хранятся в SQLite в общем bind-каталоге `/artifacts`: WAL, ожидание блокировки до 120 секунд, короткие транзакции. Это учебный односерверный стенд; для нескольких узлов витрину следует перенести в PostgreSQL. Модели и отчёты лежат рядом: `/artifacts/models`, `/artifacts/reports`.

## Ручная проверка DAG и смены модели

DAG сначала **на паузе**, чтобы проверка была воспроизводимой. Ручной запуск после снятия паузы может соседствовать с плановым: `max_active_runs=1` сериализует запуски каждого DAG.

1. Откройте Airflow, найдите `retrain_fraud_model`, нажмите Trigger DAG. В Graph видна цепочка `prepare_temporal_window → train_candidate → compare_on_same_holdout → publish_if_not_worse`. Для ручного прогона без ожидания планировщика также можно выполнить команду ниже. Команда `dags test` выполняет настоящий граф и изменяет данные стенда.

```bash
docker compose exec airflow-scheduler airflow dags test retrain_fraud_model 2026-10-21
cat artifacts/models/latest.json
ls -lh artifacts/models/
```

На чистом стенде bootstrap обучается на январе–феврале 2019, указатель исходного окна — март 2019. Первый DAG использует февраль–апрель 2019: февраль и март для train, апрель для test. Результат сравнения появляется в `artifacts/reports/evaluation-*.json`. Если обе метрики кандидата не хуже, появится `model-<hash>.joblib`, `latest.json` сменит версию и месяц. Если модель хуже, DAG успешно завершает проверку, но явно возвращает `published: false`; prod и месяц остаются прежними. Зелёный DAG сам по себе не означает публикацию — проверяйте JSON.

2. Проверьте, что скорер подхватил модель и новые сообщения содержат её версию:

```bash
docker compose logs --tail=30 scorer
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:9092 --topic scores --max-messages 5 --timeout-ms 30000
```

Консольный consumer без `--from-beginning` читает новые сообщения. При смене версии лог скорера содержит `Loaded model model-...`. Также можно посмотреть последние результаты в таблице:

```bash
docker compose exec scorer python -c "from pipeline.core import connect; print(connect().execute('SELECT transaction_id, score, fraud_flag, model_version FROM scores ORDER BY rowid DESC LIMIT 10').fetchall())"
```

Пример контракта результата:

```json
{"transaction_id":"uuid", "transaction_time":"2026-10-21 18:00:00", "score":0.73, "fraud_flag":true, "model_version":"model-<hash>"}
```

3. Запустите `supply_labeled_month` через Trigger DAG или CLI:

```bash
docker compose exec airflow-scheduler airflow dags test supply_labeled_month 2026-10-21
```

Первый запуск добавит май 2019, затем следующий запуск с другим run_id — июнь. Повторное выполнение того же run_id ничего не добавляет. Новый retrain с новым run_id возьмёт следующий месяц после **опубликованного** окна.

4. Запустите `dataset_quality` и откройте HTML по ссылке из http://localhost:8082:

```bash
docker compose exec airflow-scheduler airflow dags test dataset_quality 2026-10-21
```

5. Для работы по расписанию снимите паузу у всех трёх DAG в UI или выполните:

```bash
docker compose exec airflow-scheduler airflow dags unpause supply_labeled_month
docker compose exec airflow-scheduler airflow dags unpause retrain_fraud_model
docker compose exec airflow-scheduler airflow dags unpause dataset_quality
```

Все DAG выполняются каждые 5 минут (`*/5 * * * *`), `catchup=False`, время Airflow — UTC. У поставки и обучения независимые расписания; уже готовый апрель в seed устраняет гонку при первом старте. Если следующего месяца пока нет, prepare явно сообщает об этом и повторяется с задержкой. Сначала дождитесь supply и повторите задачу.

## Данные, окно и собственный препроцессинг

В `data/seed.csv` — воспроизводимая подвыборка учебного `train.csv` из HW1: январь–апрель 2019, по 1800 обычных и до 80 фродовых транзакций на месяц, `random_state=42`, всего 7520 строк. Исходный набор и идея стенда описаны в [коде семинара](https://github.com/NikitaMalykhin/mlops_realtime_fraud_detector_airflow). Реализация DAG, задач и признаков в этом репозитории самостоятельная. Подвыборка искусственно обогащена фродом; её метрики и порог 0.5 служат проверке механики, а не оценке реального антифрода.

Поставка создаёт **3000 строк** за запуск: детерминированно выбирает существующие строки, переносит дату в следующий календарный месяц, сохраняет время суток и обрезает день до последнего допустимого дня месяца. Новые ID уникальны: `YYYY-MM-index`. Глубина истории — **36 календарных месяцев**, включая новый месяц; всё раньше первого дня самого старого месяца удаляется. Если очистка затронула бы ещё нужное окно обучения, транзакция отменяется с понятной ошибкой: сначала нужно восстановить переобучение. Параметры `BATCH_SIZE` и `HISTORY_MONTHS` заданы в Compose.

Окно обучения всегда **3 последовательных месяца**. Первые два — train, третий — test. При успешной публикации окно сдвигается на один месяц, самый старый месяц исключается из обучающего снимка. Случайного train/test split нет. Размеченная витрина сохраняет более глубокую историю для поставки. Копирование строк между месяцами — условие учебной симуляции; оно может давать оптимистичные метрики. В реальном проекте нужны новые независимые метки и контроль повторов сущностей.

Собственный препроцессинг в `pipeline/core.py` одинаков для train и online:

- `log1p(amount)` и `log1p(population_city)`;
- циклические `sin/cos` часа, выходной и ночное время;
- расстояние до продавца по формуле haversine и взаимодействие расстояния с суммой;
- one-hot для категории, штата, пола с обработкой неизвестных значений.

Векторизатор обучается только на train и сохраняется внутри sklearn Pipeline вместе с моделью. Имена, адреса, transaction_id и target в признаки не попадают. В онлайн-сообщении target отсутствует. Скорер перед каждым сообщением читает `latest.json`, загружает новую модель целиком и затем использует её версию в результате.

## Проверка качества модели и публикация

Кандидат и текущая prod-модель оцениваются **на одних и тех же строках самого свежего месяца** нового окна. PR-AUC считается как average precision, дополнительно проверяется ROC-AUC. На несбалансированном фроде PR-AUC полезнее accuracy. Публикация разрешена, если **обе метрики не ниже** incumbent (только допуск `1e-12` на машинную арифметику). Для bootstrap применяется тот же контракт и та же версия препроцессинга. Холодный старт использует компактный лес из 20 деревьев глубины 5; DAG обучает 100 деревьев глубины 12. На включённом seed первый кандидат улучшает обе метрики и публикуется; на других данных публикация зависит от gate.

Сравнение старых метрик из разных месяцев не используется: состав данных изменяется. Качество модели не гарантируется, поэтому отказ от публикации — нормальный исход. Детерминированный кандидат, отклонённый на неизменных данных, будет снова отклонён: автоматического ослабления порога нет. При отказе указатель не движется; для продвижения нужно улучшить алгоритм/признаки или исправить данные и выполнить новый run. Отчёт хранит метрики обеих моделей, месяц holdout, число строк и решение.

## Повторы после ошибок

- Supply держит `BEGIN IMMEDIATE`: вставка строк, очистка и запись `run_id → month` коммитятся одной транзакцией. До commit ошибка откатывает всё, после commit retry находит run_id и возвращает прежний месяц.
- Prepare сначала сохраняет снимок CSV, затем план с хешем run_id. Если план есть, retry использует тот же снимок; указатель не двигается при prepare/train/evaluate.
- Train сохраняет бинарник через временный файл и `os.replace`. Повторное обучение детерминировано.
- Publish сначала сохраняет файл модели, затем атомарно заменяет **один** `latest.json`, содержащий и имя файла, и месяц окна. Ошибка до смены manifest оставляет прежнюю модель; сиротский бинарник безопасен, retry допубликует тот же месяц. Ошибка после смены manifest распознаётся по версии, второй сдвиг не происходит.
- Устаревший run не перезапишет более новую prod-модель: проверяется сохранённый incumbent. `max_active_runs=1` защищает от одновременных retrain в планировщике. Не запускайте `dags test retrain...` одновременно с другим retrain: CLI обходит ограничение scheduler.
- Kafka используется с `acks=all`, manual commit после публикации результата и записи в SQLite. Доставка at-least-once: после аварии возможен повтор в Kafka; таблица scores дедуплицирует transaction_id. Ошибочная входная транзакция вызывает ошибку без commit, её нужно исправить на стороне источника.

## Data Quality

DAG `dataset_quality`: `snapshot_dataset → write_html_and_enforce_rules`. Проверяется неизменный снимок всей витрины, без её модификации. Правила:

1. Витрина не пуста.
2. Обязательные ID, timestamp, target, категория и числовые поля не содержат NULL.
3. `transaction_id` уникален.
4. Все timestamps разбираются как даты.
5. Target содержит только 0/1 и оба класса присутствуют.
6. Сумма конечна и неотрицательна.
7. Координаты конечны и находятся в диапазонах широта ±90°, долгота ±180°.
8. Население конечно и неотрицательно.
9. Месяцы непрерывны, есть минимум три месяца.
10. В каждом месяце представлены оба класса.

Отчёт с PASS/FAIL по каждому правилу записывается в `artifacts/reports/dq-*.html` **до** ошибки задачи, поэтому неуспешная проверка тоже оставляет HTML. Этот DAG наблюдает данные отдельно; обучение дополнительно проверяет наличие всех месяцев окна и двух классов в train/test. HTML не содержит строк исходных персональных данных.

## Проверки и структура

На чистом запущенном стенде можно автоматически выполнить три DAG и проверить новую версию в реальных потоковых скорах без перезапуска контейнера:

```bash
python3 scripts/verify_stack.py
```

Результат сохраняется в `artifacts/verification.json`. Перед этой проверкой оставьте DAG на паузе и не запускайте их вручную, чтобы начальным состоянием был bootstrap.

Локальные тесты требуют Python 3.11, как и образы проекта.

```bash
python3.11 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt pytest
pytest -q
docker compose exec airflow-scheduler airflow dags list-import-errors
```

Тесты проверяют supply без дублей, календарный переход, временное окно, отказ quality gate, принятие равных метрик, падение между бинарником и manifest, retry без двойного сдвига, hot reload, отсутствие target в признаках, очистку истории с защитой ожидающего окна и HTML при DQ-ошибке. GitHub Actions выполняет тесты, проверяет Compose и импорт всех трёх DAG, а также поднимает весь стенд и проверяет сквозной цикл публикации и hot reload. Версия dill закреплена одинаково в образах Airflow и скорера: Airflow расширяет pickle, и сохранённая внутри задачи модель должна загружаться тем же десериализатором.

```
dags/                 # только сборка графов
pipeline/core.py      # хранилище, признаки и модель
pipeline/tasks.py     # функции задач с docstring о чтении, записи и повторах
services/stream.py    # Kafka simulator и scorer
data/seed.csv        # компактный датасет для запуска без загрузок
tests/               # проверки поведения и восстановления
```

Остановка: `docker compose down` (данные сохраняются). Полный сброс для повторения с bootstrap:

```bash
docker compose down -v
# Следующая команда удаляет только сгенерированные данные этого проекта,
# в том числе файлы, принадлежащие UID контейнера Airflow.
docker compose run --rm --no-deps artifacts-init sh -c 'find /artifacts -mindepth 1 -delete'
docker compose up -d --build
```

Стенд предназначен для локальной учебной проверки: стандартные пароли, без внешнего доступа к UI; порты UI привязаны к 127.0.0.1.
